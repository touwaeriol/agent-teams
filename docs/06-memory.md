# 06 记忆

目的：会话重启（崩溃、上下文压缩、节点重启、员工换节点）后，员工仍然知道自己是谁、学到过什么、任务做到哪一步。

## 三种记忆

| 记忆 | 节点上的文件 | 内容 | 谁写 | 生命周期 |
| --- | --- | --- | --- | --- |
| 员工记忆 | `memory/MEMORY.md` | 这个员工在这个项目里攒下的经验：环境的坑、约定、偏好 | 员工（`remember`）、人（Web） | 长期，有上限 |
| 任务交接 | `tasks/<任务号>/HANDOFF.md` | 目标、已完成、下一步、注意事项 | 员工（`write_handoff`） | 跟任务走，结束后归档不再注入 |
| 项目知识 | `memory/PROJECT.md` | 计划、决定、所有员工都该知道的事 | 统筹（含确认员工的提升申请）、人 | 长期，所有员工共享 |

**以控制面为准。** 三者都存在控制面（`memories`、`handoffs` 表，带版本）；节点上的文件由守护进程渲染写入，设为只读（0444），员工改文件不会生效，必须用工具。这样换节点、重装节点都不丢，人也能在 Web 上看和改。

## 写入

- **随时写**：员工学到值得记住的事就调 `remember`。模板提示词里写明规则。
- **必须写的时机**：
  - 上下文占用 ≥ 80%：控制面发系统消息让员工先 `write_handoff`；
  - 任务交付前：`report(done)` 前要求更新交接（交接随任务归档，作为任务记录）；
  - 会话被人停止（graceful）：先发一条“停止前更新交接”，等这一轮结束再停。
- **上限**：员工记忆默认 200 行。超过时 `remember` 返回提示，要求员工先用 `forget` 删掉过时条目或合并。人也可以在 Web 上整理。
- **提升**：`remember(promote=true)` 或 Web 上点“提升为项目知识”，产生一条 `pending_promotion`，统筹用 `promote_memory` 确认后进入项目知识，同项目所有员工可见（包括同模板分布在其他节点的员工）。
- 每次变化后控制面推 `memory.sync`，守护进程更新文件；会话运行中不打断，下次注入时生效（`remember` 的返回值已经告诉了员工本次写了什么）。

## 恢复

每次启动会话（新开或续跑）都先同步、再注入：

1. 控制面在 `session.start` 前确认守护进程已有最新记忆（必要时附带在 `session.start` 里）。
2. 守护进程写入 `MEMORY.md`、`PROJECT.md`、当前任务的 `HANDOFF.md`。
3. 注入：
   - **Claude Code**：`.claude/settings.json` 配置 SessionStart 钩子 `agent-teams-hook session-start`，输出三份内容作为附加上下文。SessionStart 在新开、续跑、压缩后都会触发，所以压缩后不丢。
   - **Codex**：没有对应钩子。守护进程在启动前把三份内容写进 `AGENTS.md` 里一个固定段落（`<!-- agent-teams:memory:start -->` … `end -->`），续跑时把交接作为第一条消息再送一次。

注入的内容有总长度上限（例如 8 KB），超出时优先保留交接，其次项目知识，最后员工记忆（只取最近的条目，并提示员工整理）。

## 渲染格式

```markdown
# 员工记忆（cc5 · 主线开发）
<!-- 由 agent-teams 生成，请用 remember / forget 工具修改 -->
- deploy/tests 的 e2e 依赖 staging 环境变量，先跑 make env。（11-12 · #1290）
- docs/design 下的改动要 architect 评审后再合并。（11-12 · 人）
```

```markdown
# 任务交接 #1315 staging 部署脚本重构
目标：…
已完成：
- …
下一步：
- …
注意：…
```

## 和 agent 自带记忆的关系

Claude Code 可能有自己按目录保存的记忆（存在节点的 `~/.claude` 下）。它不会同步到控制面，换节点就没了，不能作为记忆来源。实现时先确认其存放方式和开关，再决定关闭它，还是由守护进程在会话结束时把它的增量当作 `remember` 上传，避免两套记忆各记一半。见 [09-mvp.md](09-mvp.md#需要先验证的事)。
