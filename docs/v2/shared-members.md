# 项目级共享员工与任务队列

状态：设计稿（2026-11-17）；阶段 1（§2–§4、§6–§8，网页最少改动）已实现（`feat/staff-p1`），阶段 2（§5 会话管理）已实现（`feat/staff-p2`），阶段 3–4 待做。取代 architecture.md §6.1 “成员 = 讨论串 × 岗位 × count”和 §7.3 “按讨论串调度”的做法；其余章节不变。

## 1. 要解决的问题

现在每开一个讨论串就按岗位模板新建一整套成员（`InstantiateThread`，`core/employees.go`）。十个讨论串就是三四十个员工，同时活跃的会话没有上限，订阅账号的速率限制（architecture.md R2）很快被打满；小讨论串的成员大部分时间闲着，办公室里一个讨论串冒一排人。

目标：

- **员工就是员工**：一个项目按岗位配几个成员就是几个（例如 dev × 3、reviewer × 1），所有讨论串共用。同时活跃的成员会话 ≤ 成员数。
- **任务排队、员工领取**：组长拆出的任务进**项目级任务队列**，空闲成员按粘性和依赖领取；人手不够就加员工，不按讨论串设上限。
- **员工自己管理会话**：同一讨论串的下一个任务接着用原会话（上下文快满时先压缩），换讨论串就 clear 开新会话。

不变的：统筹每个项目 1 个；**组长每个讨论串 1 个、不共享**（它握着这个讨论串的全部上下文，闲时进程会被停放，成本低）；分支、worktree、合并队列、CI、PR 的规则不变。

## 2. 员工模型

| 层级 | 归属 | 数量 | 说明 |
| --- | --- | --- | --- |
| 统筹 | 项目 | 1 | 不变 |
| 组长 | 讨论串 | 每个讨论串 1 个 | 不变，名字 `lead-<讨论串号>` |
| 成员（含审查、决策岗） | **项目** | 岗位模板的 `count` | `at_employees.thread_id = NULL`，名字 `<岗位>-<n>`，项目内唯一 |

- **身份**：用户是老板 / 甲方，不是员工。统筹（项目经理）和组长（讨论串的临时项目组长）是**管理岗**：仍是员工（有会话、状态、会被提问和审批），但**不算编制、不领队列里的任务**，只安排任务。“配几个就几个”只约束成员（**执行岗**）。组长随讨论串上任、卸任，开讨论串不受编制限制（想限制同时进行的讨论串数用已有的 `max_running_threads`，超出排队，默认不限）。
- **岗位人数的含义变了**：岗位模板的 `count` 原来是“每个讨论串几个”，改成“项目编制几个”。`open_thread` 的 `roles`（按讨论串指定人数）不再有意义，只保留“这个讨论串用哪些岗位”（`only_roles`：组长只能往这些岗位派任务）；传了人数的旧调用忽略人数。
- **建在哪里**：项目第一次开讨论串时按用户当前的岗位模板建齐成员；之后岗位模板改了 `count`（加员工 / 减员工），保存模板时补建或把多出来的设为 `active = false`（手里有任务的等任务结束再停：它的任务离开 claimed / running 时再核对一次）；停用的成员没有任务时关掉它的会话。调度兜底只给有待领任务、却一个项目成员都没有的项目（迁移前的项目）建成员，不每轮重刷模板。项目设置里以后可以按项目覆盖人数，第一版用模板的 `count`。
- **成员当前在哪个讨论串**：新列 `at_employees.current_thread_id`（可空）= 它手里任务所在的讨论串，或它最近一个会话所属的讨论串。用于粘性和办公室显示，不用于权限。
- **会话**：仍然一个员工最多一个活会话（`at_agent_sessions_live`）。`at_agent_sessions` 加 `thread_id`：这个会话是在哪个讨论串的 worktree 里开的。成员换讨论串 = 关掉旧会话（`close_reason = switch_thread`）、在新讨论串的目录开新会话（不 resume，首条消息 = 交接摘要 + 任务简报）。被 `switch_thread` 关掉之后、还没在别处开新会话就回到原讨论串的，照常 resume 原会话。
- **目录和分支不变**：成员在讨论串 N 的 worktree 仍是 `projects/<pid>/threads/<N>/<name>/<repo>`，分支仍是 `thread/<N>/<name>`。共享以后同一个成员会在几个讨论串各有一个 worktree，互不干扰；讨论串结束时按“在这个讨论串干过活的成员”清理（见 §7）。
- **技能和插件目录**（`node/src/sessions/skills.ts`、`plugins.ts`）现在按 `<thread_no>/<name>` 放，改成项目级成员放 `project/<name>`。

## 3. 名字解析（谁是 dev-1）

很多表用“讨论串 + 名字”指人（`claimed_by`、`at_questions.asker`、`at_mail`、`at_merge_queue.employee`、`at_permission_rules.employee`、消息 `author` / `meta.to`、`at_events.actor`），都没有外键。共享以后名字在项目内唯一，这些列**不用改**，只改解析：

- `EmployeeByName(project, thread, name)`：先找这个讨论串自己的员工（组长；以及迁移前留下的旧成员，§8），找不到再找项目级成员。
- `ThreadEmployees(thread)`（名单、`list_team`、广播、暂停、审查岗查找、换模型）改成“讨论串参与者” = 组长 + 讨论串自己的旧成员 + **当前在这个讨论串有任务、或在这个讨论串开过会话的项目成员**。审查 / 决策岗查找（`gateRole`）改成按项目找这个岗位的成员。
- 成员工具的“当前讨论串”（`toolsvc/service.go` 的 `prepare` 现在取 `Employee.ThreadID`）改成：**调用所在会话的 `thread_id`**（会话只在一个讨论串的 worktree 里开），会话没有讨论串时取成员当前任务所在的讨论串、再取 `current_thread_id`。所以一个已被换讨论串关掉的旧会话里迟到的工具调用、用量和回复都算旧讨论串的，看不到成员在新讨论串的任务（`core.SessionContextOf` 把项目成员绑到会话的讨论串，路由的用量 / 活动 / 回复也按它）。一个成员全项目同时最多一个 claimed / running 任务（原来是每个讨论串最多一个）。

## 4. 项目级任务队列

任务表结构不变（主键仍是 `(conversation_id, id)`，id 仍按讨论串编号 `t<n>`），只是调度不再按讨论串分开：

- **可领取**：`status = 'pending'`、依赖全部 `done`（由事件维护成 `ready_at` 非空，领取查询不再逐个查依赖，见 §4.1 末尾）、所属讨论串在 `running` / `waiting`（暂停、排队、待验收的讨论串不发新任务）、岗位匹配。依赖断了的处理见 architecture.md §7.3（下游标 `blocked`）。
- **触发**：任务新建或状态变化、成员回合结束且手里没任务、节点上线、每 10 秒兜底。调度从 `Schedule(threadID)` 改成 `Schedule(projectID)`（Valkey 频道 `sched:<project>`，调度进程按前缀订阅），同一个项目一个调度循环。
- **点名**：`assign_task(assignee="dev-2")` 仍然只给 dev-2；dev-2 手里有别的讨论串的任务时排队等它。

### 4.1 谁领哪个任务

空闲成员（`active`、手里没有 claimed / running 任务）按下面的顺序挑，同一档里按优先级、关键路径（直接或间接依赖它、还没结束的任务数，多的先；存在 `at_tasks.downstream`）、可领取的时刻、创建时间：

1. **点名给它的任务**。
2. **返工预留**：审查打回、CI 失败、合并冲突修复（`fixTask`）这类“自己任务的后续”，预留给原员工；**10 分钟**没人领就放开给同岗位其他人。
3. **依赖粘性**：只依赖一个任务、且那个任务是它做的 → 优先给它（上下文还在，多半是同一批文件）。依赖多个任务时，优先给做了其中最多的那个员工。
4. **讨论串粘性**：和它当前会话同一个讨论串的任务。
5. **同仓库**的任务。
6. 其他任务。

**防饿死**：任务在可领取状态等超过 **5 分钟**，就不再讲粘性，第一个空闲的同岗位成员直接领。讨论串之间不设人数上限（人手不够就加员工）。

反过来，一个任务变成可领取时，如果有多个空闲成员，按同样的顺序挑人（对这个任务粘性最强的成员优先）。

实现（`scheduler/score.go` 的 `pick`，纯函数）：每一轮先锁项目行（`core.LockProject`：所有事件都写项目行，统一按“项目 → 成员 → 任务”的顺序加锁，和改编制、投递消息不会互相死锁），取项目的空闲成员和**空闲成员所属岗位**的可领取任务（每个岗位最多 200 个，一个岗位积压不会挤掉别的岗位），给每个（成员, 任务）组合定档，取最好的一对、不等待地锁住（`SKIP LOCKED`，再核对成员仍启用、空闲，任务仍待领）后领取，再来下一轮。补充约定：

- **档位**：点名 > 返工预留 > **饿死**（可领取超过 5 分钟：排在粘性前面，按等待时间先后）> 依赖粘性 > 讨论串粘性 > 同仓库 > 其他。预留给别人且未过期的任务对其他人直接不可见；点名的任务只给点名的人（点名的返工也一样，不会放开）。
- **同仓库**：讨论串用到的仓库（`at_thread_repos` 里的行，设了基准或建过讨论串分支才有）和成员当前讨论串用到的仓库有交集。
- **讨论串粘性**看成员的 `current_thread_id`，没有时看它活会话的讨论串。
- **岗位范围**（`only_roles`）不限制平台建的审查、决策、修复任务。
- **不审自己的活**：平台开的审查 / 决策任务，被审任务是同岗位某成员做的、而同岗位另有能领它的成员（启用、有节点、名字不同，项目成员还不能被讨论串里同名的旧成员挡住——和下面旧成员的排除口径一致）时，作者本人不领（`ClaimableTasks` 的 `not_by`）；等过饿死时限（5 分钟）同事还没领，作者也可以领，但排在最后一档（任何同事、作者的其他任务都先于它），避免同事一直忙时卡住。岗位只有一人时照常自己审。
- **旧成员**（§8）只在自己的讨论串领任务，且排在所有项目成员之后（点名给它、预留给它的除外）：池里的任务先给项目成员。
- **忙**：手里有 claimed / running 任务（在没结束的讨论串里；暂停的讨论串里的任务也算，等它恢复）。
- **回合中不换讨论串**：项目成员的活会话正在跑一个回合（`at_agent_sessions.in_turn`，`turn_started` 置位、`turn_ended` 和会话离开 active 时清掉）时，不领**别的讨论串**的任务（领了就要关掉正在跑的会话）；同讨论串的照领（简报排在回合后面）。回合结束会触发一轮调度。
- **点名给停用成员的任务**：改编制停用成员时，它待领的点名任务改成岗位任务（`assignee = 岗位`），并告诉那个讨论串的组长；调度时点名的名字已不是启用成员的，也按岗位池处理。
- **返工预留**：审查打回的任务回到 `pending`（`claimed_by` 清空），`reserved_for = 原成员`、`reserved_until = 现在 + 10 分钟`，原成员空闲时按预留档领回，简报带上审查意见；合并冲突 / CI 修复任务按原成员的岗位进队列并同样预留。过期后别人接手时，简报写明原成员的提交在 `origin/thread/<N>/<原成员>`，先 merge 进来再改。
- `ready_at` 在任务新建（没有依赖或依赖都已完成）、最后一个依赖完成、任务回到队列（重试、失败重排、返工）时写入；迁移 00270 给已可领取的旧任务补写为迁移时间。调度本身不写。
- **就绪由事件维护**（阶段 4）：领取查询只认 `status = 'pending' AND ready_at IS NOT NULL`（加讨论串状态、岗位、预留的过滤），不再对每个任务查依赖；办公室任务板的“依赖锁”用同一个判断（`core.TaskReady`）。写 `ready_at` 的地方都在 `core`：`InsertTask`（没有未完成的依赖）、`RequeueTask`（重试、失败重排、返工；依赖还没完成时清成 NULL，等依赖完成）、`SetTaskStatus` 把任务改成 `done` 时只看它的**直接下游**（`MarkReady`：还在 pending、没有 `ready_at`、依赖全部 done 的写上）。所有改状态的路径都经过这两个函数（领取 pending → claimed 不影响就绪）。依赖从“满足”变回“不满足”的路径不存在：`done` 是终态（`SetTaskStatus` / `RequeueTask` 拒绝把 done 改成别的状态，`ErrTaskDone`），重试只接受 failed / blocked / cancelled；依赖失败或取消时下游标 `blocked`（离开 pending），重试时按依赖当时的状态重新算。新任务的依赖、或重试的 blocked 任务的依赖已经 `failed` / `cancelled` 时，`assign_task` 返回错误（写明是哪个依赖、什么状态），任务页重试回 409 `dependency_ended`：这样的任务永远等不到，不能悄悄进池。
- **并发下的就绪**：READ COMMITTED 下事务看不到别人还没提交的改动，两个最后依赖同时完成、或新建 / 重排任务时它的依赖正在完成，各自事务里的判断都会以为“还有依赖没完成”。所以新建、重排、进出结束状态的事务提交后都对该讨论串做一次**收尾**（`core.Store.SettleTasks`，`Tx` 的提交后回调，每个讨论串一次）：单独的短事务，先取该讨论串的事务级 advisory 锁（只有收尾用，同一讨论串的收尾排队），再给“pending、没有 `ready_at`、依赖全部 done”的任务写上（按编号加锁），然后重算 `downstream`。最后提交的那个事务的收尾一定看得到所有依赖都已提交。状态事务里的 `MarkReady` 只是快路径，跳过别的事务锁着的下游（`SKIP LOCKED`），从不等相关任务的行锁。
- **兜底**：每 10 秒的扫描把“pending、没有 `ready_at`、依赖全部 done、2 分钟没动过”的任务补写上并打警告日志（出现就说明事件和收尾都漏了，比如提交后进程退出），部分索引 `at_tasks_unready` 让它只扫等依赖的任务；同时对没结束、还有未结束任务的讨论串重算 `downstream`（不打日志）。
- **关键路径**（阶段 4）：`at_tasks.downstream` 是直接或间接依赖它、还没结束的任务数（菱形依赖只算一次，blocked 也算）。它不在改状态的事务里维护，而由提交后的收尾和扫描整讨论串重算（`core.RecountDownstream`：从未结束的任务沿 `depends_on` 往上走、去重计数，只写变了的行，别的事务锁着的行跳过、从不等锁），是排序的 tie-break，允许短暂滞后。这样改状态的事务只锁任务自己（加上 `blockDependents` 往下游标 blocked），不会再锁上游：完成 X 和取消 / 失败依赖 X 的 P 同时发生时，不会出现“X 等 P、P 等 X”的死锁（`TestStatusChangesNeverDeadlock` 两个事务各自先锁住自己的任务再同时改，反复 60 轮）。每个岗位最多取 200 个候选时也按“优先级、关键路径、可领取时刻、创建时间”截断。
- **性能**（阶段 4，`scheduler/perf_test.go`）：一个项目 20 个讨论串、500 个任务（每个讨论串 5 条依赖链）、10 个成员，一轮调度（锁项目、空闲成员、可领取任务、打分、锁定并领取）中位数约 18 ms、最慢约 40 ms（目标 < 100 ms）；改动前同样的数据中位数约 34 ms、最慢约 70 ms；审查修复（收尾移到提交后）后在负载 13～20 的测试机上中位数 17～26 ms、最慢 41～58 ms。测试按时间判定，`go test -short` 跳过，界限放宽到 250 ms，只拦数量级的退化，数字以日志输出为准。领取查询只取打分用的列（选中的任务锁定时再读整行），点名检查只对点名任务做，并加了 `at_tasks_ready`、`at_employees_thread` 索引。

### 4.2 任务衔接：后续任务怎么接着前面的成果做

依赖任务 `done` = 它的成员分支已经合进讨论串分支（审查、决策、合并队列都过了）。后续任务要在**代码**和**上下文**两层都接上：

**代码：开工前同步工作目录（现在缺这一步，不只是共享以后才有的问题）。** 现在成员领任务时平台不碰他的 worktree：`git.prepare` 看到 worktree 已存在就直接返回（`node/src/git/jobs.ts` `worktreeLocked`），合并队列合完也不更新成员分支，所以 dev-1 领到“基于 dev-2 的 t3 继续”时，目录里没有 t3 的代码。改成领取时先发带同步的 `git.prepare`（`sync: {mode, ref}`，守护进程 feature `git_sync`）：

1. `git fetch`。
2. 成员分支上**没有未合并的提交**（都已进讨论串分支，正常情况）且工作区干净 → 把成员分支重置到最新的讨论串分支（`checkout -B thread/<N>/<name> origin/<讨论串分支>`）。
3. 有未合并的提交（返工、合并冲突修复这类接着自己没合完的活）→ 把最新的讨论串分支 merge 进成员分支；冲突就停下，任务简报里写明冲突文件，让成员先解决。
4. 工作区有未提交的改动（上一个任务没收干净）→ 不动，简报里提醒先处理。

同步结果（新的 HEAD、是否有冲突）记在任务上，任务简报里写出“你的分支已同步到讨论串分支 <sha>，包含 t3（dev-2）的改动”。

**依赖等合并，不叠分支。** 后续任务只在依赖合进讨论串分支后开工，不从前置任务的成员分支直接切出（叠分支在前置任务被打回时要一起 rebase，容易乱）。前置任务排队审查时，靠 §4.1 的依赖粘性让同一个人接着做：他的分支本来就带着自己的提交。

**上下文：任务简报带上前置任务的交接内容。** 现在只有每个依赖 500 字的总结。改成每个依赖给出：

- 谁做的、完整总结（上限放到 3000 字）；
- 合进讨论串分支的提交范围和改动文件列表（合并队列里有 trial / merge 的 sha，用 GitHub compare 取文件列表），附一句“用 `git log <范围>` / `git show <sha>` 看细节”；
- 前置任务的审查意见（审查岗打回或通过时写的说明）和它发布的交付物；
- `complete_task` 新增可选的 `handoff` 字段：“给接手的人”的说明（还没做完的、要注意的坑、约定好的接口），提示词要求有下游依赖的任务必须写。简报里原样转给后续任务。

### 4.3 跨节点协同

成员可能在不同的机器上（dev-1 在 rc-erio，dev-2 在 cvp）。**代码只经 GitHub 交换，节点之间不直连**：

- 每台节点每个仓库一份自己的共享克隆，成员的 worktree 挂在上面。`complete_task` 时平台先替成员把成员分支推到 GitHub；合并队列在 GitHub 上合（试合并、`UpdateRef`），不在任何节点上合。所以讨论串分支的“真相”永远在 GitHub，§4.2 的同步第一步就是 `git fetch`，在哪台节点上都一样。
- **只在一台节点上的东西**要单独对待：
  - 未推送的提交和未提交的改动：成员中途被迫换节点（节点离线超过 `rehome_after`、节点被删）会丢。对策：成员每个回合结束时，平台把成员分支上已提交但未推送的提交自动推一次（推到成员分支本身，不影响讨论串分支）；提示词继续要求勤提交。未提交的改动无法保住，交接摘要里如实写明“上一个会话在 X 节点上有未提交的改动，已丢失”。
  - 会话记录（Claude 转录、Codex rollout）：只能在原节点 resume。换节点 = clear + 交接摘要（现有 `handoff` 机制）。
  - 依赖安装、构建缓存：每台节点各自装，第一次在一台节点上做某个讨论串会慢一些。
- **成员不绑节点，每次开新会话按用量挑**（`orchestrator/nodepick.go`）：项目级成员建出来时先按节点轮流记一个节点（`at_employees.node_id`，同一岗位尽量分开，Codex 只分到隔离节点），但这只是“上次在哪”。每次开**新**会话都重新挑：候选节点里在线、该运行时已登录（守护进程报 `auth: none` 的不算）的节点，先排有空槽且额度没满（任一窗口 < 95%）的，再按**负载分**从低到高排：负载分 = 该运行时的订阅用量（百分数）+ `SessionWeight`（10）× 节点上的活跃会话数（`core.ActiveSessionCount`：不是 closed / parked / crashed 的会话）。用量——Claude 看 5 小时、每周和员工模型所属的每周窗口（如 Fable、Opus），Codex 看全部窗口，已过重置时间的窗口不算，没有用量数据按 50% 算。这样新会话在多个可用节点间分摊：用量低的节点多分，但不会独占（用量每分钟才刷新一次，只看用量时在它涨上来之前所有新会话都会去同一台）；例如 A 用量 0%、已有 3 个活跃会话（30）输给 B 用量 20%、没有会话（20）。负载分打平时留在原节点（克隆和缓存还在），再看空槽多少，最后按节点列表顺序（创建时间）。活跃会话数在开会话的事务里数（同一项目的开会话按项目行锁排队，前一个已提交的新会话状态是 opening，会被数到）。每次选节点记一条 info 日志 `pick node`（员工、项目、讨论串、stay、每个候选的 node / node_id / rt / usable / online / used / active / free / score、选中的节点和是否 hold）。只有必须留下时才不挑：要 resume 原对话或在本讨论串已有 worktree，且原节点在线、还是候选、额度没满；否则换节点，resume 改成交接摘要（同 `handoff`）。没有任何可用节点时留在原节点等它上线。
- **一个岗位可以配多种 agent**（`at_roles.runtimes`，如 `[claude, codex]`；`runtime` 是第一个，`model` 是第一个的模型，`models` 按运行时存其余的模型）：每次开新会话把岗位每种运行时的候选节点放在一起，按上面同一套规则挑（运行时, 节点）——哪种 agent 在哪台节点上剩余额度最多就用哪个，所以 Claude 和 Codex 按额度均衡轮着用。必须留下时运行时也不变；换了运行时，resume 改成交接摘要，员工的 `/model` 选择（上一种运行时的模型 id）清空，`at_employees.runtime` 记成新的运行时。岗位去掉某种运行时后，正用它的员工回到岗位的第一种运行时。Codex 仍只派隔离节点：没有隔离节点时多运行时岗位只会用其他 agent（岗位页提示），只配了 Codex 的岗位仍然报错。统筹和组长只能用能当组长的运行时（Claude Code）。
- **领任务不看节点**：粘性已经让成员尽量留在同一个讨论串；换讨论串只是在同一台节点上多建一个 worktree（共享克隆已有，`git worktree add` 很快）。节点离线时，它上面成员的任务回到队列（现有 `SessionLost` → 回池），由其他节点上的同岗位成员领，代码照常从 GitHub 拿到。
- **审查岗也走同一套同步**：审查任务开工前，把审查员的 worktree 切到被审任务 `complete_task` 时推送的提交（`pushed` 里每个仓库的 sha；只读检出）。
  - 审查员是项目共用成员，常常是“切到这个讨论串后的第一次审查”，这时它在本讨论串还没开过会话、worktree 也不存在：review 同步照样发（不受“在本讨论串开过会话”的限制），由同步作业在会话将要打开的节点上新建 worktree 并检出被审提交，之后才发简报。（#22 修复：之前这条路径直接打开会话，worktree 从讨论串分支新建，审查员看到的不是被审代码，审完被当成驳回。）
  - 守护进程声明 `git_review_sha` 时同步带 `expect_sha`，守护进程负责重新 fetch 和核对；不管守护进程新旧，控制台收到结果都逐仓库核对 HEAD 和被审 sha（任务没推送过的仓库不核对）。不一致、作业失败或 2 分钟没回结果，都不发简报：同一次领取内再准备 2 次；还不行算**平台错误**——审查任务回到队列重新领取（不是驳回，被审任务保持 `review`，不退给开发者）；累计 `MaxAttempts` 次后审查任务置 `blocked`，通知组长“平台错误：审查工作树没准备好”，用户在任务页重试即可。
  - 简报和审查说明里写出每个仓库被审提交的完整 sha，平台核对过的写“平台已检出并核对，HEAD = <sha>”。没法核对时（守护进程没有 `git_sync`、clone 模式），简报让审查员先自己确认看到的是被审改动（只读会话用不了 git，`gitdir` 下的 HEAD 也在工作树外读不到，所以用 Grep / Read 查开发者总结里提到的改动文件和标识是否存在），找不到就用 `complete_task(status="platform_error")` 上报——它不算驳回，走上面的平台错误路径；`platform_error` 只能用在平台派的审查 / 决策任务上。
- 组长不写代码，它在自己节点上读讨论串分支，同样在需要时同步。

## 5. 会话管理：继续、压缩、清空

成员领到下一个任务时，平台按下面的规则决定怎么开工，然后才送任务简报：

| 情况 | 做法 |
| --- | --- |
| 同一讨论串，上下文用量 < 岗位的 `compact_between_pct`（dev 默认 60%） | 直接在原会话里发任务简报 |
| 同一讨论串，用量 ≥ `context_limit × compact_between_pct`（没设上限就按运行时报的窗口） | 先压缩，再发任务简报；节点不支持 `session_compact` 时改为 clear |
| 同一讨论串，这个会话已经连续做满 `clear_after_tasks` 个任务（dev 默认 8，审查岗 1） | clear：关掉会话，开新会话 |
| 换讨论串 | clear：关掉会话，在新讨论串的 worktree 开新会话 |
| 讨论串结束 | 关掉成员在这个讨论串的会话（成员本身不受影响） |

- **不每个任务都压缩**：压缩要多花一个回合、会丢细节，完整上下文的缓存命中也更省钱。只按用量阈值压缩；Claude Code 自己快满时也会自动压缩。
- **clear 后的第一条消息** = 任务简报 + 讨论串交接摘要（组长是谁、主任务计划、这个成员在这个讨论串以前做过的任务和结果），沿用 `handoffSummary` / `threadDigest` 的做法，只换成按“成员 × 讨论串”取。
- **实现**（`scheduler/session.go`）：判断表是纯函数 `decideStep`，先看 clear（会话已收到的任务简报数 `at_agent_sessions.tasks_done` ≥ `clear_after_tasks`），再看压缩（上次回合结束记下的 `context_used`）。会话正在跑回合、还在启动或崩溃了就不动它（直接发简报）。压缩时任务停在 `claimed`（`at_tasks.compact_id`），收到 `session.compacted`（不管成功与否；守护进程等空闲最多 2 分钟、压缩最多 7 分钟，崩溃、重启、一直忙都会回 `ok: false`，见 protocol.md §4.10）或 10 分钟后再走开工前同步，同步完才发简报——两段等待串起来，每段超时按 `wait_since` 算。clear = 以 `context_clear` 关会话，简报照常投递时开新会话，`continuation` 看到这个关闭原因就在前面加 `[新会话]` 摘要（换讨论串的 `[换讨论串]` 摘要同一个函数）。旧守护进程（没有 `context_usage`）不报用量，就只按任务数 clear。

### 5.1 按岗位配置（员工模板）

压缩分两种，都配在岗位模板上（`at_roles` 新列，YAML 视图 `context:` 段），项目不单独覆盖：

| 字段 | 含义 | 由谁执行 |
| --- | --- | --- |
| `context_limit` | 这个岗位的**上下文上限**（token，例如 600K，至少 100K：会话开局的提示词和工具就占 15–25K，Claude 最晚在窗口 − 33K 压缩）；下面的百分比都相对它，不相对模型本身的窗口（1M 的模型设 600K，60% 就是 360K）。超过模型窗口时按窗口算（领取时取 `min(上限, 上次报的窗口)`；Codex 的任务中阈值同样封顶）。不填 = 模型窗口（上次会话报的窗口；还没报过时见下面“没设上限”） | — |
| `compact_between_pct` | 任务之间：领下一个任务时已用上下文 ≥ `context_limit × 比例` 就先压缩 | 平台（§5.3 `session.compact`） |
| `compact_in_task_pct` | 任务进行中：已用上下文到 `context_limit × 比例` 时运行时自己压缩 | 运行时：Codex 设 `model_auto_compact_token_limit = context_limit × 比例`（绝对 token 数）；Claude 设 `CLAUDE_CODE_AUTO_COMPACT_WINDOW = context_limit`，`CLAUDE_AUTOCOMPACT_PCT_OVERRIDE` 换算成相对有效窗口的百分比（§5.2 实测）。改了在下一个会话生效 |
| `clear_after_tasks` | 同一会话连续做满几个任务后 clear（0 = 不按次数 clear） | 平台 |
| `compact_focus` | 压缩时要保留什么（一段话），拼进压缩指令 | 平台 + 钩子（§5.2） |

建议的默认值（新建岗位时按岗位类型填，用户可改）：

| 岗位 | 任务间 | 任务中 | 连续几个后 clear | 理由 |
| --- | --- | --- | --- | --- |
| 写代码的成员（dev 等） | 60% | 80% | 8 | 同一讨论串的任务常常前后关联，留着上下文划算 |
| 审查 / 决策岗 | — | 80% | **1** | 每次审的是不同的分支，上一次的上下文只是噪音，每个任务都 clear |
| 组长 | 不适用（不领池里的任务） | 70% | 不适用 | 计划、任务、提问都在平台里，压缩丢不了要紧的东西 |
| 统筹 | 不适用 | 70% | 不适用 | 讨论串列表和状态随时能查 |

例：岗位 `context_limit = 600K`、任务间 60%、任务中 80% → 领任务时已用 ≥ 360K 先压缩，任务中到 480K 自动压缩，与模型是不是 1M 窗口无关。模型窗口只有 200K 时按 200K 算：任务间 120K，Codex 任务中 160K，Claude 由 CLI 把窗口夹到 200K（约 74%，因为 PCT 是按 600K 换算的）。

**没设上限**（`context_limit` 为空）：控制台把这个员工上一个同运行时会话报的窗口作为 `session.open.context.window_tokens` 发下去，任务中阈值 = 窗口 × `compact_in_task_pct`（Codex 设成绝对 token 数；Claude 不设窗口，只把 PCT 换算到 `窗口 − 20K` 上）。员工还没有会话报过窗口时：Codex 不设阈值（用 Codex 自己的默认），Claude 的 PCT 直接用 `compact_in_task_pct`，即 CLI 有效窗口（窗口 − 20K）的这个比例。任务间的比例一直按上一个回合报的窗口算，没报过就不按用量压缩。

团队页的岗位弹窗按这些规则显示实际阈值：Claude 的任务中阈值超过 `窗口 − 33K`（窗口 = 上限夹到 100K～1M）时显示封顶后的值。

任务中阈值不要设太低：每次压缩多花一个回合、丢细节；Claude Code 自己的默认阈值已经接近满窗口，80% 是给长任务留出余量。

### 5.2 单个任务很长、任务中途就压缩了怎么办

1. **压缩后补“任务锚点”**：压缩会把任务说明压成摘要，长任务容易跑偏。平台在压缩完成后（Claude 的 `compact_boundary` / SessionStart(`compact`) 钩子，Codex 的 `thread/compacted`）给成员补一条短消息：任务 id、原始任务说明、分支、依赖的交接说明、目前已报的进度（`report_progress`）。Claude 用 SessionStart 钩子的 `additionalContext` 注入（不占一条用户消息），Codex 在压缩后用 `turn/steer` 插进还在跑的回合。
2. **压缩指令带重点**：平台主动压缩时发 `/compact <compact_focus + 当前任务锚点>`；运行时自己压缩时用 PreCompact 钩子补同样的指令（钩子返回的 `systemMessage` 会拼进压缩指令，见下面的实测）。dev 的默认重点：“保留当前任务 id、分支、改过的文件、做过的决定、还没做完的事和已知的坑”。
3. **进度落盘**：提示词要求长任务定期 `report_progress`，并把工作笔记写到 worktree 里 git 忽略的 `.agent-notes/<任务id>.md`；压缩、clear、换节点都丢不掉。
4. **任务太大要反馈给组长**：同一个任务在任务中压缩了 2 次以上，平台给组长发 `[Task t5 · dev-1] 任务很长，已压缩 2 次，考虑拆小`。拆分质量会越来越好。
5. **记指标**：每个任务记任务中压缩次数、开始和结束时的上下文 token 数（`at_tasks.compactions` / `ctx_start` / `ctx_end`），在团队页按岗位看（阶段 3），用来调阈值。

**实测（SDK 0.3.325，`node/scripts/smoke-compact.ts`，小模型、窗口调到 100K，约 0.11 美元）**：

- **a. `Query.getContextUsage({detail: "summary"})`**：返回 `totalTokens`（当前上下文 token 数；只开 Read 工具的空会话约 7–8K）、`maxTokens` = `rawMaxTokens`（衡量用的窗口：设了 `CLAUDE_CODE_AUTO_COMPACT_WINDOW` 就是它，否则是模型窗口，1M 模型默认按 200K 的压缩边界）、`percentage`。`summary` 不调计数接口，回合结束后调用很便宜。
- **b. 自动压缩阈值**：`CLAUDE_CODE_AUTO_COMPACT_WINDOW` 是 token 数（也接受 `600k`），夹在 100K～1M 之间并且不超过模型窗口；阈值 = `min(有效窗口 × PCT / 100, 有效窗口 − 13K)`，有效窗口 = 窗口 − 20K（给摘要输出留的余量），`CLAUDE_AUTOCOMPACT_PCT_OVERRIDE` 可以是小数。实测窗口 100000、PCT 30 → 阈值 24000：18.7K 不压缩，24.25K 在下一次请求前自动压缩（`compact_boundary` trigger `auto`，回合中途也会触发）。所以守护进程按 `window = clamp(context_limit)`、`PCT = context_limit × compact_in_task_pct / (window − 20K)` 设置（`node/src/sessions/claude/compact.ts`）：600K、80% → 窗口 600000、PCT 82.76 → 480K 压缩，1M 模型也一样。`context_limit` 低于 100K 时窗口按 100K 算、PCT 照样换算到目标 token 数。
- **c. 平台主动压缩**：往提示队列推一条用户消息 `/compact <指令>` 就行，依次收到 `status: compacting` → `status: null, compact_result: success` → `system/init` → `compact_boundary`（trigger `manual`、`pre_tokens`、`post_tokens`）→ `result`（success，正文为空）。守护进程以 `compact_boundary` 之后的 `result` 作为完成。
- **d. PreCompact 钩子**：没有 `hookSpecificOutput`，但 SDK 回调钩子返回的 `systemMessage` 会作为附加压缩指令，和 `/compact` 后面的指令拼在一起（摘要里出现了只在钩子里要求的暗号）。所以自动压缩时由钩子补 `compact_focus + 锚点`；平台主动压缩时指令已经在 `/compact` 里，钩子不再重复。
- **e. SessionStart(`compact`)**：自动和手动压缩之后都会触发，返回的 `additionalContext` 能被模型看到（压缩后问只写在 `additionalContext` 里的暗号，答对了）。所以 Claude 的锚点走这个钩子，不额外发消息。

**按实测选的做法**：Claude 的锚点走 SessionStart(`compact`) 钩子的 `additionalContext`，自动压缩的重点和锚点走 PreCompact 钩子的 `systemMessage`；平台主动压缩发 `/compact <compact_focus + 下一个任务>`（这时上一个任务已经结束，守护进程清掉旧锚点，钩子不再补）。Codex 没有压缩指令参数，`compact_focus` 只对 Claude 生效；Codex 运行时自己压缩后，回合还在跑就用 `turn/steer` 把锚点插进当前回合（不用 `later`：`later` 要等回合结束，那时任务可能已经交了），回合已经结束就不补。

**任务锚点**的内容（`orchestrator/anchor.go` `TaskAnchor`，≤ 7500 字）：讨论串号和任务 id、原始说明、成员分支、依赖任务的交接说明、最近一次 `report_progress`（存在 `at_tasks.progress`）和工作笔记路径 `.agent-notes/<任务id>.md`。平台主动压缩的指令用同一段内容（换成“接下来要做…”的开头）。锚点随任务简报下发一次（`session.send.anchor`，开新会话时是 `first_message.anchor`），之后报的进度不会再推给守护进程——压缩后模型按锚点去读工作笔记。锚点只属于手上的任务：`complete_task` 的结果和成员没有任务时收到的消息都带 `anchor: ""` 清掉它；会话崩溃重开或守护进程重启后重开、首条消息又不带锚点时，`session.open.anchor` 带上手上任务的锚点。任务重新排队（失败重试、返工、手动重试）或被重新领取时，`progress` 和长任务指标清零。

### 5.3 协议改动（节点）

- `session.event` 的 `turn_ended` 带上 `context: {used_tokens, max_tokens}`：Claude 用 `Query.getContextUsage({detail: "summary"})`，Codex 用 `thread/tokenUsage/updated` 的 `last.totalTokens` / `modelContextWindow`。控制台存到 `at_agent_sessions.context_used` / `context_max`（token），比例在领取时按岗位的 `context_limit` 算。
- 新命令 `session.compact {session_id, open_gen, compact_id, instructions}` → 守护进程：等当前回合结束，Claude 发一条 `/compact <instructions>` 用户消息，Codex 调 `thread/compact/start`；完成后发现有的 `compacting` 事件（on → off）和 `session.compacted {session_id, open_gen, compact_id, ok, context}`（键都是 `compact_id`，控制台按它找到等着的任务）。控制台等到 `session.compacted`（或 10 分钟超时）再同步、送任务简报。
- `session.open` 加 `context {limit_tokens, in_task_pct, focus}`（岗位快照里的值），`session.send` 和 `first_message` 加 `anchor`。
- clear 用 `session.close`（新原因 `context_clear`；没有 `session_compact` 的旧守护进程收到 `switch_thread`，效果一样）+ 不带 resume 的 `session.open`。
- `hello.features`：`context_usage`、`session_compact`。

## 6. 平台工具和提示词

- 组长：`assign_task` 的说明改成“任务进项目队列，由空闲的同岗位成员领取；写实例名就点名”。组长名单（`roster`）显示项目成员和他们当前在哪个讨论串。
- 成员：提示词里说明“你是项目的固定成员，会轮流给不同讨论串干活；每个任务开始时看任务简报里的讨论串号和分支”。`list_team`、`ask_lead`、`send_message` 都按当前任务所在的讨论串。
- 成员的 git 身份（`gitIdentity(name)`）不变。
- **跨讨论串的消息**（用户直接发给成员、组长转达、对成员问题的回答等记在某个讨论串的消息）：消息记在那个讨论串，事件也发在那个讨论串。收信的项目成员不在那里干活时：手里没任务（也不在回合中）就换到那个讨论串（`MoveToThread`）再收；手里有别的讨论串的任务就推到它当前的会话，开头写 `[#12 · 来自 用户 的留言]`（回答是“的回答”），不换讨论串。不带记录位置的投递（留言推送、平台通知）在成员没有当前讨论串时只存不推，**不会**记到统筹的对话里。
- **跨讨论串的留言**（`send_message`、`broadcast`）：留言存在发信人所在的讨论串（`at_mail.conversation_id`），讨论串页的留言列表照旧。收信人是项目成员、而它正在别的讨论串干活（或不在任何讨论串）时，平台把留言推到它**当前的会话**，开头写 `[#12 · 来自 lead-12 的留言]`（广播是“的广播”），**不为此换讨论串**；同讨论串的仍是 `[Message from lead-12]`。它没有开着的会话、也没有当前讨论串时只存不推，下次领任务时看。`read_messages` 列出它当前任务所在讨论串的未读留言并标为已读，另外提一句“其他讨论串还有发给你的未读留言：#12 2 条”（只算直接发给它的，不算广播），到那个讨论串干活时再用 `read_messages` 看。任务简报里的“你有 N 条未读留言”也只算任务所在讨论串的。

## 7. 讨论串结束和清理

- `EndThreadWork`：关闭会话改成按 `at_agent_sessions.thread_id = 讨论串` 关（组长 + 在这个讨论串开着会话的成员），不再按 `e.thread_id`。
- 删除成员分支（`deleteMemberBranches`）和清理目录（`at_thread_nodes` 路径）改成遍历“在这个讨论串领过任务的成员”（`SELECT DISTINCT claimed_by FROM at_tasks WHERE thread_id = …`）加讨论串自己的旧成员。
- 删除讨论串时不再级联删成员（项目级成员 `thread_id` 为空，本来就不会被级联）。

实现（`core.ThreadWorkers`、`delivery/cleanup.go`）：“干过活的成员” = 讨论串自己的旧成员 + 项目成员里领过这里任务的（名字被这里同名旧成员占用的算旧成员）、在这里开过会话的（`at_agent_sessions.thread_id`）、当前在这里的，**停用的也算**（分支和目录还在）。项目成员在讨论串 N 的 worktree 开会话时就记进 `at_thread_nodes`（和组长一样），所以 `git.cleanup` 照旧按 `at_thread_nodes` 的路径清；删除讨论串时 `git.purge projects/<pid>/threads/<N>` 发到 `at_thread_nodes` 的节点、组长的节点和这些成员的节点。讨论串结束时清空指向它的 `current_thread_id`。

## 8. 迁移（上线时正在跑的讨论串怎么办）

- 迁移给每个项目按岗位模板建项目级成员。名字和旧的讨论串成员一样（`dev-1`），但旧成员 `thread_id` 非空，唯一键 `(project_id, COALESCE(thread_id,''), name)` 不冲突，不用改。
- 正在跑的讨论串：旧成员手里已经 claimed / running 的任务让它做完；**之后所有新领取只给项目级成员**（调度只看 `thread_id IS NULL` 的成员），旧成员做完手里的任务就闲置，讨论串结束后照常清理。
- 名字解析“先找讨论串自己的、再找项目级的”（§3），所以旧讨论串里提到的 dev-1 仍然指旧成员，不会串。
- 已经 `pending` 的任务直接进项目队列。
- **00270 的 Down 只回退表结构，不是功能回滚**：它删掉新加的列，但上线后开的讨论串只有组长、成员是项目级行（`thread_id` 为空），旧代码不认识这种数据。要回退只能连同数据一起处理（或从备份恢复）。
